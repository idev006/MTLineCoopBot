# บทที่ 8 กระบวนการพัฒนา (Development Process)

**หลักการของโครงการ:** Document-Driven · Agile Kanban · Dashboard สำหรับทีม

## 8.1 หลักการ Document-Driven (เอกสารนำโค้ด)

**เอกสารคือสัญญา (Contract) — โค้ดต้องเขียนตามเอกสาร ไม่ใช่วิธีกลับกัน**

### 8.1.1 กฎเหล็ก 5 ข้อ

| # | กฎ | คำอธิบาย |
|---|-----|----------|
| 1 | ออกแบบในเอกสารก่อนเสมอ | ฟีเจอร์/การเปลี่ยนแปลงทุกอย่าง ต้องมีบท/หัวข้อในเอกสารเล่มนี้ก่อนเริ่มเขียนโค้ด |
| 2 | โค้ดต้องตรงตามเอกสาร | โครงสร้างฟิลด์, item id, API contract, สถานะ, กฎความ valid — ทุกอย่างต้องตรงกับที่เอกสารกำหนด |
| 3 | เมื่อออกแบบเปลี่ยน ต้องแก้เอกสารด้วย | การแก้เอกสารเป็นส่วนหนึ่งของงาน ไม่ใช่งานเพิ่มภายหลัง |
| 4 | ตรวจด้วย Contract Test | โค้ดต้องผ่านการตรวจสัญญา (เช่น `verifyMenuContract`) ก่อนถือว่าเสร็จ |
| 5 | ป้ายสถานะใน README คือความจริง | `✅ ทำแล้ว` / `📌 ออกแบบไว้ — เฟส X` ต้องอัปเดตทันทีเมื่อโค้ดเปลี่ยนสถานะ |

### 8.1.2 วงจรการทำงาน (Workflow)

```text
ความต้องการ / ปัญหา
        ↓
1. ออกแบบในเอกสาร (บทที่อ้างอิง) — เขียนข้อกำหนด/สัญญาไว้ก่อน
        ↓
2. เปิดการ์ดใน KANBAN.md (อ้างอิงหัวข้อเอกสาร)
        ↓
3. Implement โค้ดตามเอกสาร
        ↓
4. ตรวจสอบ: syntax + contract test (Test.js) + เอกสารยังตรงกับโค้ด
        ↓
5. อัปเดตป้ายสถานะใน README (✅) และปิดการ์ด → Done
```

### 8.1.3 Definition of Done (DoD) — ครบทุกข้อถึงจะปิดงานได้

> **อัตโนมัติผ่าน CI:** GitHub Actions (`.github/workflows/ci.yml`) รัน `node --check` + ชุดทดสอบสัญญา 17 ชุด (`scripts/ci-test.js` — verifyMenuContract / verifyThaiCaptions / testVerifyLineSignature / testVerifyWebhookSecret / testMemberValidity / testWelcomeMenu / testMemberRepository / testMemberDataService / testSeedData / testFinanceData / testColumnReordering / testDateValidator / testDateConverter / testExpiryStatus / testExpiryService / testCoreMemberRules / testLoanCalculator) + secret scan 2 ชั้น (regex ใน `ci-test.js` + **gitleaks** ตาม `.gitleaks.toml` ตรวจประวัติ git ทั้งหมด) ทุก push ขึ้น `main` — ครอบคลุม**ข้อ 2 และ 3** ของ DoD โดยอัตโนมัติ

- [ ] โค้ดตรงตามเอกสาร (บท/หัวข้อที่การ์ดอ้างอิง)
- [ ] Contract test ผ่าน (`verifyMenuContract` / `verifyThaiCaptions`)
- [ ] `node --check` ผ่านทุกไฟล์ที่แก้
- [ ] ป้ายสถานะใน README อัปเดตแล้ว
- [ ] เอกสาร (ถ้าออกแบบเปลี่ยน) ถูกแก้ให้ตรงกับโค้ดแล้ว
- [ ] การ์ดใน KANBAN.md ย้ายไป Done

## 8.2 Agile Kanban

ใช้ Kanban แบบเบา (Lightweight) เหมาะกับทีมเล็ก — เน้นลิมิตงานระหว่างทำ (WIP) และดึงงานตามความพร้อม ไม่มีพิธีกรรมหนัก

### 8.2.1 คอลัมน์ของบอร์ด (ดูไฟล์ `KANBAN.md`)

| คอลัมน์ | ความหมาย | WIP Limit |
|---------|----------|-----------|
| 📥 Backlog | งานที่ยังไม่ได้เริ่ม อยู่ใน Roadmap (ระยะ 2–4) | ไม่จำกัด |
| 📋 To Do | งานที่เลือกทำรอบนี้ (Sprint) แล้ว | ไม่จำกัด |
| 🔄 In Progress | กำลังทำอยู่ | **2–3 การ์ด** |
| ✅ Done | เสร็จตาม DoD ครบ | — |

### 8.2.2 กติกา

1. **ดึงงาน (Pull)** — ไม่มีใครถูกสั่งงาน; แต่ละคนดึงการ์ดจาก To Do เข้า In Progress เมื่อพร้อม
2. **WIP Limit** — อย่าทำเกิน 2–3 การ์ดพร้อมกัน (โฟกัสให้เสร็จมากกว่าเริ่มเยอะ)
3. **การ์ด 1 ใบ = งาน 1 เรื่อง** — เล็กลงจนเสร็จภายใน 1–3 วัน; ถ้าใหญ่เกินไป แตกการ์ดย่อย
4. **รูปแบบการ์ด:** `[MT-XX] เรื่อง` + ลิงก์หัวข้อเอกสาร + Checklist DoD
5. **ย้ายการ์ดเมื่อสถานะเปลี่ยนจริง** — ป้ายสถานะใน README ต้องตรงกับบอร์ด

### 8.2.3 การวางแผนรายสัปดาห์ (ประจำสัปดาห์ ~15 นาที)

1. ทบทวนบอร์ด: อะไรค้างใน In Progress / อะไรเสร็จแล้ว
2. เลือกงานจาก Backlog มาใส่ To Do (ตามลำดับความสำคัญของ Roadmap บทที่ 7)
3. ตรวจว่าเอกสารอ้างอิงของงานพร้อมหรือยัง (ถ้ายัง → ต้องออกแบบในเอกสารก่อน)

## 8.3 Dashboard สำหรับทีม (Project Management Dashboard)

ใช้ข้อมูลเดียวกันจากที่เดียว 3 ระดับการมอง:

| ระดับ | เครื่องมือ | ใช้ดูอะไร | อัปเดตเมื่อไหร่ |
|-------|-----------|-----------|----------------|
| ผู้บริหาร | **README.md → ตารางสถานะ** | ภาพรวมฟีเจอร์ (✅/📌) + ความคืบหน้าโครงการ | เมื่อปิดการ์ด/เปลี่ยนสถานะ |
| ทีมพัฒนา | **KANBAN.md** | งานที่ทำ/ค้าง/กำลังทำ + WIP | ต่อเนื่อง (ทุกครั้งที่ย้ายการ์ด) |
| เมตริก | **Google Sheets Dashboard** — `createDashboard()` ใน `app/Dashboard.js` | KPI 5 ตัว (8.3.2) + Burndown + WIP/Cycle + DoD (ดู [metrics-dashboard-template.md](./metrics-dashboard-template.md)) | รายสัปดาห์ + บันทึกต่อเนื่อง |

### 8.3.1 แนวคิด Dashboard (ข้อมูลเดียว แสดงหลายมุม)

```text
                        ┌─────────────────────────────┐
                        │   แหล่งข้อมูลเดียว (SSOT)     │
                        │  - KANBAN.md (การ์ดงาน)      │
                        │  - README (สถานะฟีเจอร์)     │
                        │  - บทที่ 7 (Roadmap)         │
                        └──────────────┬──────────────┘
                 ┌─────────────────────┼──────────────────────┐
                 ▼                     ▼                      ▼
        ┌─────────────────┐  ┌──────────────────┐  ┌──────────────────┐
        │ Exec Dashboard  │  │ Team Kanban      │  │ Metrics Dashboard│
        │ (README status) │  │ (KANBAN.md)      │  │ (Sheets, เฟส 4)  │
        └─────────────────┘  └──────────────────┘  └──────────────────┘
```

### 8.3.2 ตัวชี้วัดที่แนะนำ (KPI)

| KPI | สูตร | เป้าหมาย |
|-----|------|----------|
| อัตราเสร็จงานต่อสัปดาห์ | จำนวนการ์ด Done / สัปดาห์ | ≥ 2–3 |
| WIP เฉลี่ย | การ์ด In Progress เฉลี่ย | ≤ 3 |
| งานค้าง (Backlog) | จำนวนการ์ดใน Backlog | ลดลงต่อเนื่อง |
| Cycle Time | วันตั้งแต่ To Do → Done | ≤ 5 วัน |
| ความถูกต้องตามเอกสาร | % การ์ดที่ผ่าน DoD ครบ (รวม doc sync) | 100% |

## 8.4 บทบาทของทีม (Roles)

| บทบาท | หน้าที่ |
|--------|---------|
| Product Owner | จัดลำดับ Backlog, กำหนดความต้องการ, ตรวจผลลัพธ์ |
| Developer | ออกแบบในเอกสาร → Implement ตามสัญญา → รัน test |
| Reviewer | ตรวจว่าโค้ดตรงเอกสาร + ผ่าน DoD ก่อนปิดการ์ด |

> ทีมเล็ก 1–3 คน บทบาทอาจซ้อนกันได้ แต่หน้าที่ "ตรวจสอบตรงตามเอกสาร" ต้องมีคนทำเสมอ ไม่ใช่คนเดียวกับผู้เขียนโค้ด

## สรุปท้ายบท

กระบวนการของโครงการคือ **เอกสารนำโค้ด** (เอกสารเป็นสัญญา โค้ดต้องตาม) + **Kanban แบบเบา** (บอร์ดใน `KANBAN.md`, WIP ≤ 3, ดึงงาน) + **Dashboard 3 ระดับ** (README / KANBAN / Sheets ในอนาคต) — เริ่มใช้กับงานต่อไปทันที โดยอ้างอิง DoD ครบ 6 ข้อก่อนปิดการ์ดทุกใบ
